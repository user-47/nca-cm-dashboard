Findings from inspecting the existing repo before adding the Poster Creator.
Written 2026-08-16.

## Host ports

Taken by the existing stack: `3000` dashboard, `5432` db (loopback), `9000`/`9001` MinIO,
`5678` n8n, `8880` kokoro (profile-gated).

**Free and claimed for this work: `3100` templates, `3200` render-api.**

Note the handoff assumed the dashboard was on `3300`. It is on **`3000`**, so
`NEXT_PUBLIC_DASHBOARD_URL=http://localhost:3000`.

## Decisions taken

The owner's instruction was to prefer what already exists over the handoff document
where the two disagree.

1. **Presigned URLs, not a public bucket.** Every existing read goes through
   `presignGet`. The bucket also holds sermon audio and announcement video, so making
   it public to serve posters would expose all of it. `/render` returns a presigned
   URL and stores the object key.
2. **Brands are org-scoped.** Every table in this schema carries `org_id`, and
   `requireUser()` hands back an `orgId`. A global `brands` table would let one church
   render with another's brand, so `brands` gets an `org_id` FK and an `is_default`
   flag. An org has many brands, which is also what makes "save as new brand" from a
   reference poster sensible: it must not mean "create a new church".
3. **`orgs.theme_json` stays as dashboard chrome only.** `brands.tokens` is the poster
   design system. They overlap in spirit but govern different surfaces, and conflating
   them would make a poster palette change repaint the admin UI.
4. **`poster_tmpls` is dropped and replaced by `templates`.** The old table was created
   in the Phase 1 migration but never read or written by any code. Carrying both would
   mean two answers to "what templates exist".
5. **npm workspaces, not pnpm.** Adding a `workspaces` key to the existing
   `package.json` is a one-line change. Migrating to pnpm would mean regenerating the
   lockfile the working Dockerfiles depend on.
6. **NCA seeds with the real product fonts** (Spectral, IBM Plex Sans, IBM Plex Mono),
   not the Fraunces + Inter the handoff proposed. Posters should look like the rest of
   the product. Fraunces + Inter stays available as one of the curated pairs for other
   brands.
7. **`claude-sonnet-5`** for reference-poster style extraction. The model id in the
   handoff was stale.

## Verified in this task

- `npm install` succeeds; all four workspaces link into `node_modules/@nca/`.
- `npx tsc --noEmit` on the existing app: clean.
- `npx next build` on the existing app: compiles successfully.
- `docker compose build app`: succeeds. The `npm ci` in the deps stage tolerates the
  new `workspaces` key even though workspace manifests are not copied into that stage.

## Known risks carried forward

- **The app Dockerfile's `npm ci` will break once the workspaces gain real
  dependencies.** It copies only the root `package.json` and `package-lock.json`, then
  runs `npm ci`. That is fine today because the workspace packages have no external
  deps. When render-api takes on Playwright and Fastify, the lockfile and the copied
  manifests will disagree. Fix at that point: `npm ci --workspaces=false` in the app's
  deps stage, so the dashboard image never pulls Playwright.
- **`.dockerignore` does not exclude `services/` or `packages/`,** so they land in the
  app build context. Harmless now. If the dashboard later imports `@nca/render-client`,
  they must stay included and Next needs `transpilePackages` for them.
- **Workspace packages export TypeScript source,** not built `dist/`. Consumers must
  transpile them (`transpilePackages` in Next, `tsx`/`tsc` in render-api). This avoids
  a build step in the dependency graph but is a constraint to remember.

## Unrelated issue noticed

There are two n8n Dockerfiles. `n8n/Dockerfile` is the one compose builds. A newer
root `Dockerfile.n8n` is better in two ways: it pins versions (n8n 2.10.4, static
ffmpeg 7.1, alpine 3.22) and it adds `curl` and `openssl` with their shared libraries,
which closes the missing-`curl` gap found earlier.

It is missing one thing the current file has: creating `/data/work`, `/data/jobs`,
`/data/out` and chowning them to `node`. On a fresh install the `pipeline-work` volume
starts empty and root-owned, so the render script would fail to create its working
directory. Consolidating on the root file plus that `RUN mkdir -p … && chown` line
would be strictly better than either. Left alone in this task since it is not Poster
Creator scope.

## Task 3 notes

**Fonts are fetched, not committed by hand.** `npm run fonts:fetch` reads
`FONT_REGISTRY` and downloads the latin subset of each declared face into
`services/templates/public/fonts`. The registry is the source of truth, so
adding a weight there and re-running is the whole workflow. 17 faces, ~300 KB
total. A test asserts every file the registry promises exists on disk, because a
missing face is synthesised silently by the browser and ships a poster in the
wrong weight with nothing reporting a problem.

**Next 15.1.3 has a published CVE** (CVE-2025-66478) and npm warns on install.
The templates app is pinned to 15.5.23.

**The root tsconfig excludes `services/`.** The dashboard is React 18 and the
templates app is React 19; type-checking the latter from the root judges React 19
components against React 18 types and fails on JSX that is valid in place. Each
app runs its own `typecheck`.

**Do not run `next dev` and `next build` against the same `.next`.** Killing a
dev server mid-write leaves a directory that is half dev and half production, and
`next start` then fails with `Cannot find module './994.js'`. Wipe `.next` before
building for production.

**Port hygiene.** `pkill -f "next dev"` does not reliably kill the server, because
npx spawns a child whose command line differs. Kill by listening port instead:
`Get-NetTCPConnection -LocalPort 3100 -State Listen` then `Stop-Process`. A
lingering process on 3100 caused a production server to fail with EADDRINUSE while
curl happily kept talking to the old one.

**Cold-start renders vary.** The first two or three responses after `next start`
differ before output stabilises. Once warm, ten consecutive fetches are
byte-identical. render-api must wait for `/api/health` before it trusts a render,
not merely for the port to accept connections.

## Task 5 notes

**Two bugs that only a rendered pixel would have found.** This is the argument
for running Task 5 before Task 4.

1. *The quote card rendered at 1px.* `base = min(w,h)/1080` evaluates to `1` at
   1080px, and it was used directly as the root `font-size` rather than as a
   multiplier. Every `em` in the template was therefore relative to 1px: padding
   of 7px, a headline of 6.5px. The markup was correct, the tokens were correct,
   the HTML inspected clean. Only the PNG showed it.
2. *A hanging image URL hung the render forever.* `page.evaluate` has no timeout
   of its own, so an image request that never settles — neither `load` nor
   `error`, just pending — leaves the promise unresolved. It held a pool context
   hostage and the HTTP request never returned. The in-page wait now carries its
   own deadline.

**No deviceScaleFactor: 2.** The handoff suggested it for crispness, but the
templates size themselves in real pixels: a request for 1080x1350 builds a
1080x1350 canvas. Doubling device scale would return a 2160x2700 PNG for a
request that said 1080, contradicting the API's own width and height. Contexts
run at scale 1. A genuine 2x print variant needs its own pool and is deferred
rather than faked with an option that silently does nothing.

**Object keys are content-addressed**, not random uuids: sha256 of brand tokens,
template, version, params, size, and format. Re-rendering an unchanged poster
overwrites the same object instead of littering the bucket, and "did this
change?" becomes a key comparison rather than an image diff. Verified: 26 poster
assets, 26 distinct keys, 26 objects in MinIO.

**A render produces an ordinary `assets` row with kind `poster`**, so a finished
poster is immediately usable as a section poster in the announcement builder and
is served through the same presigned-URL path as everything else.

### Measured

- Single render, 1080x1350: **620-670ms**, 39KB.
- 8 concurrent renders against a pool of 3: **2.08s** total, 8/8 succeeded, pool
  returned to idle cleanly.
- 12 renders with `PLAYWRIGHT_CONTEXT_MAX_USES=2` to force recycling: 12/12
  succeeded, pool healthy afterwards.
- Byte-identical output: five renders of identical input produced one hash.

## Task 4 notes

All three templates render at 1:1, 4:5, and 9:16. `npm run posters:matrix <scratch>
<brandId>` renders the whole grid and reports dimensions, size, and timing.

**A presigned URL cannot be a template's image source.** Building the two
hero-using templates surfaced this immediately: the URL is signed for the address
a *browser* uses (`localhost:9000`), and the host is part of the SigV4 signature,
so it cannot be rewritten for the compose network. Inside the templates container
`localhost` is that container, so every hero render died on PAINT_TIMEOUT.

The fix is that templates reference images by **object key**, and the templates
app resolves them through its own `/api/image/[...key]` route using compose-network
credentials. One relative path then works from both sides: the person's browser
loading the preview, and headless Chromium taking the screenshot. The image slot
validator accepts a key or an absolute URL, and the dashboard stores the key.

This also makes stored params portable. A poster saved today still renders after
the stack moves to a different host, which a baked-in presigned URL would not.

**Dates are formatted by hand, not with `toLocaleDateString`.** The preview runs
in the person's browser and the render runs in a headless Chromium pinned to
en-GB/UTC, so anything locale-aware would show one date while typing and print
another. `lib/format.ts` parses the ISO string as calendar parts and derives the
weekday with Zeller's congruence, never constructing a Date, so a poster dated the
30th cannot slide to the 29th because the renderer sits west of UTC. Checked
against UTC `Date` for every day across four years, plus leap days and the 1900 /
2000 century rule.

**Templates receive brand identity**, not just tokens, so a poster can sign itself
with the church's name. Brands ship without a logo file and templates fall back to
the name as a wordmark, which makes a missing logo a design choice rather than a
gap.

### Measured

- announcement: 84-105 KB, 649-685 ms across the three ratios.
- sermon-series: 277-447 KB, 682-748 ms (a photographic background, so larger).
- quote-card: 36-40 KB, 599-632 ms.

## Task 7 notes

**Model: `claude-opus-5`, not `claude-sonnet-5`.** The recon doc originally
recorded Sonnet 5 as the extraction model. The current Anthropic guidance is to
default to Opus 5 unless a model is explicitly named, and never to downgrade for
cost on the reader's behalf — that is the owner's decision to make deliberately.
Changed in `config.ts`, `docker-compose.yml`, and `.env.example`.

**Structured outputs replace prompt-and-retry.** The original plan was to ask
for strict JSON, parse it, and retry once on failure. The API constrains the
response to a JSON Schema instead (`output_config.format`), so motifs and font
tags cannot come back as something no template can draw. The retry loop is gone.

**The schema is hand-written, and validation runs twice.** The SDK's
`zodOutputFormat` helper targets Zod 4 while this workspace is on Zod 3, and
structured outputs reject the `pattern` and length constraints `brandTokens`
carries — so a generated schema would have to be stripped anyway. Writing it out
keeps what the model is told in step with what it can satisfy. Enum members are
read from the Zod enums, so a new motif or font tag cannot be added to the design
system and silently go unoffered. The full `brandTokens` schema, patterns
included, then runs client-side on the result — that is what catches a
plausible-looking `rgb(46,74,60)` that the API-side schema would accept as a
string.

**Refusals are checked before reading content.** A safety classifier can decline,
and that arrives as a normal HTTP 200 with an empty `content` array. Indexing
`content[0]` first would throw something unhelpful instead of reporting what
happened.

**The reference upload is kept whichever way the read goes.** A reference that
produced a bad answer is the only evidence for diagnosing why, and the failure
reason is written to `reference_posters.error_text` rather than leaving a
mystery null.

**Errors are typed per SDK exception class** — auth, rate limit, bad request,
connection — rather than string-matched, each with a message written for a
volunteer. A missing API key is a 501 naming the variable to set, not a 500.

## Design-quality notes

The first posters the system produced were competent and generic. Against the
church's own reference posters the gap was not the model, it was the design
system: posters are HTML screenshotted by Playwright, so nothing can appear in a
render that the templates cannot express. Four things were missing.

**Poster display faces.** All five `displayFontTag` values were editorial serifs
and text sans. Added `slab-poster` (Alfa Slab One), `sans-condensed-heavy`
(Anton), `sans-black` (Archivo Black), `caps-tall` (Bebas Neue), and
`caps-display` (Staatliches), plus curated pairs for each. Additive: brands
already saved keep validating, and the style extractor reads its enum from
`displayFontTag.options`, so the vision model started offering the new faces with
no edit to the schema.

**`motifs` was a dead token.** It was in the schema, extracted by Claude vision,
stored, and shown in the brand form — and no template read it. Every poster
rendered with no texture. `components/Motifs.tsx` now draws it. Grain is what
makes gold read as printed rather than filled.

**Logos never rendered.** `logoUrl` was threaded all the way to `TemplateProps`
and then hardcoded `null`. Now resolved through the assets table to an
`/api/image/<key>` path. A presigned URL cannot be used here: it is signed for
the browser's host, and the renderer is on another network.

**No layered assets.** Added the `cutout` slot type, validated exactly like
`image`, positioned above the artwork and below the type.

### Two composition bugs worth remembering

Both were invisible in markup and obvious in the PNG, which is the third and
fourth time that has been true on this feature.

*Sizing type on character count is blind to the face.* Alfa Slab One sets about
35% wider than Spectral at the same pixel size, so a title that fitted as an
editorial serif ran past both margins as a slab. Titles are now fitted to the
available width using the face's average advance, with the longest word setting
the hard limit because a word cannot break. The arithmetic is deliberate —
measuring in the browser would make a render depend on layout timing, and renders
have to stay byte-identical.

*Scrim strength is a composition decision, not a legibility one.* The first pass
crushed the hero to 0.42 brightness under a radial scrim, which left the top of
the frame an empty void. Overcorrecting to 0.62 let the photograph fight the
title. It now runs dark through the title zone, opens in the middle where the
photograph earns its place, and closes again at the foot so a cutout has
something to stand against.

### Verification harness caveat

`npm run posters:matrix` rendered a quote card and reused it as the hero for
every other template. That is fine for checking dimensions and byte size, and
actively misleading when looking at the output: the card's own text bleeds
through every poster and reads as a layout bug. It now takes a real photograph's
object key as its third argument. Pass one whenever you intend to look at the
renders rather than count them.

### The cutout timeout, and the bug hiding under it

First real use of a cutout returned `PAINT_TIMEOUT` after 28 seconds. Two
separate faults, one stacked on the other.

**The cutout key was never rewritten.** The render page turned object keys into
`/api/image/<key>` paths with `if (slot.type !== "image") continue`, so a cutout
kept its bare key. The browser resolved it against the render path and that
`<img>` never arrived. The underlying mistake was that "which slot types carry an
object key" lived in three places — the validator, this loop, and the dashboard
form — and only two of them learned about `cutout`. It is now one exported fact,
`isImageSlot`, used by all three, with a test that derives the answer from the
validator rather than restating it. Breaking `IMAGE_SLOT_TYPES` back to
`["image"]` fails that test, which was checked rather than assumed.

**A broken image could hang any render.** The paint wait skipped images that were
already loaded with `img.complete && img.naturalWidth > 0`. An image that had
*failed* is also complete, but with zero width, so it fell through to listeners
for `load` and `error` events that had already fired — and nothing resolved it.
Any bad URL, not just a cutout, burned the full render budget while holding a
pool context. `complete` alone is the right test: finished is finished, and a
broken image should leave a gap in the poster rather than block it. A missing
hero now renders in 847ms instead of timing out at 28s.

The timeout also logged only its error code, so working out which poster had
failed meant reading the database. The error handler now logs the template,
brand, dimensions, and params — text and object keys, never bytes or credentials.

Re-verified after both fixes: 63 tests, three typechecks clean, 9/9 matrix, and
five renders of the cutout poster to one sha256.
